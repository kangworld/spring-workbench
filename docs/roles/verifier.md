# 검증 역할

## 적용 조건

백엔드 변경에 필요한 테스트를 설계하거나 실행하고, 회귀 위험과 미검증 범위를 확인합니다.

## 책임

[검증 인덱스](../guidance/verification/README.md)에서 공통 기준과 사용 기술의 검증 문서를 선택합니다. Java 테스트는 [Java 코딩 기준](../guidance/development/implementations/java/coding-conventions.md), 저장 동작은 [영속성 지침](../guidance/persistence/README.md)을 함께 확인합니다.

## 기본 원칙
- 테스트 기본 원칙, 범위, 필수 엣지 케이스, 안정성과 검증 증거는 [테스트 기준](../guidance/verification/common/testing.md)를 따릅니다.
- 테스트 대상 선정은 요구사항과 구현 변경의 영향 범위를 우선합니다.
- 작업 담당자가 재현할 수 있도록 실패 케이스와 미검증 범위를 남깁니다.
- 테스트 실패는 `현재 변경으로 인한 실패`, `기존에 존재하던 실패`, `판단 불가`로 분류합니다. 판단이 모호하면 보수적으로 `현재 변경으로 인한 실패`로 처리합니다.
- 현재 변경으로 인한 실패는 실행 결과와 원인을 밝히고, 검증 완료 상태에 반영합니다.
- 버그를 재현해 수정한 경우에는 같은 시나리오를 다시 잡아내는 회귀 테스트를 남기는 것을 기본으로 합니다.
- 테스트 범위는 변경된 코드 실행 경로와 실제 사용자 흐름을 함께 기준으로 잡습니다.

실패 분류 예시:
- 변경한 서비스, DAO, API, 상태 전이 경로와 직접 연결되는 실패는 `현재 변경으로 인한 실패`로 분류합니다.
- 현재 작업 범위와 무관하고 기존 코드나 기존 환경에서 동일하게 재현되는 실패는 `기존에 존재하던 실패`로 분류합니다.
- 외부 환경 불안정, 공용 테스트 인프라 문제, 근거 부족으로 원인을 단정하기 어려우면 `판단 불가`로 두되, 모호하면 `현재 변경으로 인한 실패` 쪽으로 보수적으로 처리합니다.

테스트 작성 규칙:
- 프레임워크/버전은 프로젝트 표준을 따릅니다.
- 테스트 코드 스타일과 주석 규칙은 [기술별 검증 지침](../guidance/verification/README.md#기술별-검증)을 따릅니다.

검증 우선순위:
1) 도메인 규칙/상태 전이
2) 예외/경계 조건
3) 데이터 정합성(저장/조회/집계)
4) 동시성/멱등성
5) 성능 민감 경로(필요 시)

작업 절차(요약):
1) 요구사항과 구현 변경점 분석
2) 영향 범위 기반으로 unit, integration, E2E 중 어떤 조합이 필요한지 결정하고 코드 실행 경로 / 사용자 흐름 단위 테스트 케이스 설계
3) 테스트 코드 작성 및 실행
4) 실패한 테스트를 `현재 변경`, `기존 실패`, `판단 불가`로 분류하고 근거를 정리
5) 버그 수정이 포함된 경우 동일 시나리오를 잡는 회귀 테스트 추가 여부 확인 및 반영
6) 누락 시나리오, 사용자 흐름 공백, 잔여 리스크, 미커버리지 정보를 확인할 수 있게 정리
