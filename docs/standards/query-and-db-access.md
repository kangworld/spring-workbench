# 쿼리 작성/DB 접근 규칙

본 문서는 구현과 스키마 문서 사이에서 DAO와 쿼리 설계 기준을 맞추기 위한 공통 규칙입니다.

## 1) 기본 원칙
- DB 접근은 대상 프로젝트의 공통 템플릿과 추상화를 우선 사용합니다.
- 회사 표준 JDBC 스택을 쓰는 프로젝트는 `gamebox-orm-jdbc`, `DataDaoJdbcSupport`, `JdbcTemplate` 계열을 우선합니다.
- 네이티브 쿼리는 필요한 경우에만 사용하고 범위를 최소화합니다.
- 파라미터 바인딩을 기본으로 하여 SQL 인젝션을 방지합니다.

## 2) DAO 책임
- Repository/DAO는 데이터 조회/저장 책임만 갖고 비즈니스 규칙은 서비스/도메인 계층에 둡니다.
- 조회 메서드는 단건, 목록, 집계 등 실제 사용 패턴 기준으로 분리합니다.
- 대량 조회는 페이징/배치 처리를 기본으로 고려합니다.
- 갱신은 필요한 컬럼만 최소 범위로 수행합니다.

## 3) 네이티브 쿼리 사용 기준
- 조인, 서브쿼리, 집계는 목적과 범위를 명확히 기록합니다.
- 한 번에 필요한 결과를 얻도록 쿼리 수를 최소화합니다.
- 표현 전용 데이터를 위해 스키마를 왜곡하지 않습니다.

## 4) 성능/안전 체크
- N+1 가능성을 점검하고 조인, 배치, 캐시로 개선합니다.
- 페이징 또는 범위 제한을 명시합니다.
- 조건, 정렬, 조인 키의 인덱스 사용 여부를 확인합니다.
- 대량 처리나 풀스캔 가능 구간은 운영 영향과 함께 기록합니다.

## 5) 트랜잭션과 락
- 변경 작업은 트랜잭션 범위를 최소화합니다.
- 동시성 충돌 가능 구간은 락 전략이나 멱등 처리 방식을 명시합니다.
- 재시도 정책이 필요한 구간은 별도로 분리합니다.

## 6) 문서화 기준
- 요구사항 문서에는 조회/갱신 주체와 실패 케이스를 남깁니다.
- 스키마 문서에는 접근 패턴, 인덱스 근거, 정합성 보장 방식을 남깁니다.
- 전역 규약 예외가 필요한 경우 이유와 호환성 영향을 명시합니다.
