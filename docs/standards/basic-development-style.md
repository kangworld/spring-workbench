# 기본 개발 스타일

본 문서는 특정 프로젝트/프레임워크에 종속되지 않는 SVD 공통 개발 스타일과 횡단 원칙을 정의합니다.
구현 시에는 본 문서와 프로젝트별 요구사항/스키마/코딩 컨벤션을 함께 준수합니다.
세부 설계 규칙은 각 전문 문서를 단일 진실원으로 사용합니다.

## 변경 이력
- 2026-06-19: 핵심 메서드 흐름, helper 추상화 수준, 재사용, 네이밍, 주석 및 논리 블록 구성 기준을 보강했습니다.

## 1) 적용 범위
- 패키지(또는 모듈) 구성, 계층 분리 기준은 `docs/standards/architecture-guidelines.md`를 따릅니다.
- 데이터 접근 계층(Repository/DAO) 설계 원칙은 `docs/standards/query-and-db-access.md`를 따릅니다.
- 서비스/구성/배치 패턴은 `docs/standards/architecture-guidelines.md`, `docs/standards/basic-development-style.md`를 함께 따릅니다.
- 모델/DTO/VO 기준은 `docs/standards/entity-modeling.md`를 따릅니다.
- 예외/검증/보안 기본 원칙은 본 문서를 따르고, 테스트 기본 원칙은 `docs/standards/testing-guidelines.md`를 따릅니다.

## 2) 코드 스타일
- 클래스/타입은 명사, 함수/메서드는 동사 기반으로 작성합니다.
- 이름만으로 의도가 드러나도록 축약어 사용을 최소화합니다.
- boolean 변수와 메서드는 `is`, `can`, `has`처럼 상태나 가능 여부가 드러나는 이름을 사용합니다.
- 메서드는 한 가지 책임에 집중하고, 과도한 길이/중첩을 피합니다.
- 핵심 메서드는 주요 업무 절차가 위에서 아래로 읽히도록 구성합니다.
- 핵심 메서드의 호출부만 읽어도 검증, 조회, 변경, 후속 처리, 저장, 로그 같은 큰 흐름을 파악할 수 있어야 합니다.
- helper는 호출부의 업무 흐름을 더 명확하게 만들거나, 실제 재사용 또는 독립적인 테스트 가치가 있을 때 분리합니다.
- 단순 getter, 단순 위임, 한 번만 사용하는 한 줄 계산을 helper로 과도하게 분리하지 않습니다.
- 하나의 핵심 메서드에서 호출하는 helper는 가능한 한 비슷한 업무 단계와 추상화 수준을 유지합니다.
- 단일 라인 조건문이라도 중괄호 사용을 권장합니다.
- 포맷터는 프로젝트 표준 하나로 통일하고, 의미 없는 대량 포맷 변경은 피합니다.
- 네이밍은 도메인 의도와 업무 단계(검증, 조회, 갱신, 지급, 로그 등)가 드러나게 작성합니다.
- 짧은 메서드나 조건문을 한 줄로 압축하지 않고 프로젝트 포맷에 맞춰 구조를 드러냅니다.
- 반환, 분기, 예외 처리처럼 논리 흐름이 전환되는 지점은 적절한 빈 줄을 사용해 경계를 드러냅니다.
- 메서드명은 의미가 드러나는 범위에서 간결하게 유지하며, 이름이 길어지는 경우 책임이 과도하게 합쳐졌는지 먼저 검토합니다.

## 3) 주석과 의도 표현
- 주석은 코드가 아닌 의도와 제약을 설명할 때만 작성합니다.
- "무엇"보다 "왜"를 설명합니다.
- 변경으로 의미가 달라지면 주석도 즉시 함께 수정합니다.
- TODO는 맥락과 후속 액션을 함께 기록합니다.
- 서비스 레이어와 핵심 로직은 의도, 안전장치, 운영상 주의점을 설명하는 주석을 남깁니다.
- 핵심 메서드에서 업무 단계의 전환이 코드 구조와 이름만으로 충분히 드러나지 않으면 짧은 단계 주석을 남깁니다.
- 검증, 조회, 상태 변경, 외부 연동, 저장, 로그처럼 책임이 전환되는 구간은 주석 누락 여부를 완료 전에 확인합니다.
- `대상을 조회한다`처럼 코드 표현을 그대로 반복하는 주석은 작성하지 않고, 해당 단계의 업무적 역할이나 순서상 이유를 설명합니다.
- 기록/모델 필드는 필요하면 짧은 라벨형 주석을 사용합니다. 예: `// 도루`, `// KBO gameId`
- 짧은 라벨형 `//` 주석 끝에는 마침표를 붙이지 않습니다.
- 설명형 주석도 장황하게 쓰지 않고, 코드만으로 알 수 없는 이유나 제약만 남깁니다.
- enum 상수처럼 항목 자체가 공개 규칙을 나타내는 경우 항목별 JavaDoc을 붙여 의미를 바로 확인할 수 있게 합니다.
- private 생성자만 필요한 유틸 클래스는 프로젝트에서 Lombok을 사용하는 경우 `@NoArgsConstructor(access = AccessLevel.PRIVATE)`를 우선 사용합니다.
- 타입을 시그니처에 직접 쓸 때는 완전 수식명 대신 import를 사용합니다. 예: `Predicate<String>`
- 이벤트/리스너 기반 로직은 등록 지점과 콜백 흐름을 함께 추적합니다.
- 시간과 정책 기준값은 프로젝트의 정책/유틸 클래스를 통해 일관되게 가져옵니다.
- 구현 완료 전에는 변경 파일의 주석 누락, 낡은 주석, 스타일 위반을 반드시 재검증합니다.
- 예시: `TODO(auth): 토큰 갱신 정책 확정 후 만료 검증 로직 분리`

## 4) 메서드 배치와 재사용
- 검증, 조회, 상태 변경, 후속 처리, 로그처럼 의미가 유사한 메서드는 가까이 배치합니다.
- 같은 검증이나 계산이 둘 이상의 위치에서 동일한 업무 의미로 사용될 때 공통화를 검토합니다.
- 이름이나 코드 형태만 비슷하고 호출 맥락이나 업무 의미가 다르면 억지로 공통화하지 않습니다.
- 공통화로 인해 임시 객체, 불필요한 순회, 복잡한 파라미터 전달이 늘어나면 분리된 구현을 유지하는 편이 나은지 검토합니다.
- 공통화와 추상화는 코드 줄 수 감소가 아니라 호출부의 이해, 변경 범위 축소, 일관성 확보에 실질적으로 도움이 될 때 적용합니다.

## 5) 구성과 운영 관점
- 환경 의존 설정은 코드와 분리하고, 기본값과 오버라이드 방식을 문서화합니다.
- 외부 연동 설정(타임아웃, 재시도, 서킷브레이커)은 운영 기준으로 명시합니다.
- 배치 작업은 재실행 안전성(멱등성)과 장애 복구 절차를 고려합니다.
- 스케줄러 작업은 실행 주기, 락 정책, 실패 재시도 기준을 명시합니다.
- 장애나 버그 수정은 재현 조건, 원인 가설, 확인 증거를 확보한 뒤 최소 수정 원칙으로 반영합니다.
- 동일 증상에 대한 수정 시도가 3회 실패하면 땜질을 멈추고 구조 리스크나 설계 문제로 승격해 기록합니다.
- 리소스성 마스터 데이터(예: 에셋/이미지/코드성 마스터)는 DB 반영과 리소스 배포를 하나의 변경 단위로 관리합니다.
- 신규 마스터 모델 추가 시 Editor/DAO/리소스 등록(`CodeGenConfig`, `ResourceConfig`, `SqlResourceConfig`) 누락 여부를 체크리스트로 검증합니다.
- 운영 반영 순서(DDL -> 마스터 데이터 등록 -> 이미지/리소스 배포 -> 기능 오픈)를 문서에 명시합니다.
- 클라이언트 공유 스펙(필드, nullable, 상태 값)을 서버 모델/리소스와 함께 동기화합니다.

## 6) 예외와 로깅
- 도메인 예외와 인프라 예외를 구분합니다.
- 클라이언트 노출 메시지와 내부 로그 메시지를 분리합니다.
- 로그에는 추적에 필요한 최소 맥락(요청 ID, 도메인 키)을 포함합니다.
- 민감정보/개인정보는 로그 마스킹 또는 기록 제외를 기본으로 합니다.

## 7) 보안과 입력 검증
- 서버 측 입력 검증(길이/형식/범위/허용 값)을 필수 적용합니다.
- 인증/인가 실패와 비즈니스 검증 실패를 명확히 구분합니다.
- 데이터 저장/전송/로그 전 과정에서 민감정보 최소 수집 원칙을 적용합니다.
