# 아키텍처 가이드라인

본 문서는 SVD에서 요구사항, 스키마, 구현 문서를 연결할 때 사용하는 설계 기준입니다.
요구사항 문서와 구현 메모는 아래 항목을 기준으로 핵심 결정을 남겨야 합니다.

## 변경 이력
- 2026-06-19: 유스케이스 오케스트레이션 순서, 검증·조회 비용, 정책 추상화 기준을 보강했습니다.

## 1) 설계 체크리스트
- 기능 요구사항: 핵심 유스케이스, 행위자/권한, 도메인 규칙
- 비기능 요구사항: 성능, 보안, 확장성, 관측성
- 영향 범위: 변경 파일, 모듈, 데이터, 배치, 외부 연동
- 데이터 흐름: 입력, 저장, 조회, 이벤트, 실패 경로
- 테스트 전략: 단위, 통합, 회귀 포인트

## 2) 아키텍처 리뷰 프로세스
1) 현재 구조와 기존 패턴 파악
2) 요구사항과 제약 명확화
3) 대안 비교와 트레이드오프 기록
4) 결정 사항을 문서 또는 ADR로 고정

## 3) 구조와 계층 기본 원칙
- 패키지 또는 모듈은 도메인/기능 경계와 계층 책임이 함께 드러나도록 구성합니다.
- 계층 책임을 명확히 분리합니다. (API, Application/Service, Domain, Infrastructure)
- 의존성 방향은 상위 정책에서 하위 구현으로 단방향을 유지합니다.
- 순환 참조와 계층 우회를 금지합니다.

## 4) 일반 계층 책임
- API 계층: 요청 파싱, 인증/인가 연계, 응답 매핑
- Application/Service 계층: 유스케이스 오케스트레이션, 트랜잭션 경계
- Domain 계층: 비즈니스 규칙, 상태 전이, 불변성
- Infrastructure 계층: DB/캐시/메시징/외부 API 연동

## 5) 설계 원칙
- 관심사 분리: 단일 책임, 높은 응집, 낮은 결합
- 확장 가능성: 수평 확장, 캐싱, 큐, 배치 확장 여지 고려
- 유지보수성: 일관된 패턴, 테스트 용이성, 문서 정합성
- 보안: 최소 권한과 경계 보호를 설계에 반영하고, 보안/검증의 세부 기준은 `docs/standards/basic-development-style.md`를 따릅니다.
- 성능: 불필요한 호출 최소화, 효율적 쿼리, 큰 작업의 단계 분리
- 고정된 유스케이스 흐름과 변경 가능한 정책·선택·계산 규칙을 구분합니다.
- 정책 종류나 외부 환경에 따라 구현이 실제로 교체될 가능성이 있고 호출부를 단순하게 만들 수 있을 때 인터페이스 분리를 검토합니다.
- 한 번만 사용되고 변화 가능성이 낮은 단순 로직에는 확장 가능성만을 이유로 추상화를 추가하지 않습니다.

## 6) 회사 내부 프로젝트 기본 레이어
- 대상 프로젝트가 회사 표준 스택을 따르는 경우 `Controller -> Service -> Dao -> Model` 흐름을 기본으로 사용합니다.
- Controller는 요청 파싱, 최소 입력 검증, 응답 매핑에 집중하고 비즈니스 로직은 두지 않습니다.
- Service는 유스케이스 단위로 구성하고, 유스케이스 오케스트레이션, 도메인 규칙, 상태 전이, 트랜잭션 경계를 담당합니다.
- 트랜잭션은 필요한 경계에만 적용합니다.
- Dao는 데이터 조회/저장 책임만 가지며 도메인 규칙은 서비스/도메인 계층에 둡니다.
- 검증은 가벼운 것부터 수행하고, 조회 기반 검증은 필요한 최소 횟수로 묶어 처리합니다.
- 멱등성과 동시성 제어(락/버전/중복 방지 키)는 설계 단계에서 명시합니다.

### 6.1) 유스케이스 오케스트레이션 순서
핵심 서비스 메서드는 기능에 필요한 단계만 선택하되, 일반적으로 다음 순서를 기준으로 업무 흐름을 구성합니다.

1. 처리 시각, 요청자, 정책 버전 등 처리 기준 확정
2. DB 조회 없이 가능한 요청값·형식·범위 검증
3. 상위 대상 또는 이후 조회의 기준이 되는 대상 조회
4. 상위 대상의 존재, 상태, 권한 검증
5. 처리에 필요한 정책 또는 기준 데이터 조회
6. 하위 목록, 상세, 집계 등 종속 데이터 조회
7. 종속 데이터와 정책 조건 검증
8. 옵션과 분기 조건에 따른 부가 처리
9. 비용, 수량, 상태 등 변경 대상 반영
10. 결과와 후속 작업 조건 생성 및 실행
11. 변경 데이터 저장
12. 감사·운영 로그 기록
13. 응답 생성 및 반환

- 모든 기능을 위 순서에 억지로 맞추지 않고, 트랜잭션 경계와 데이터 의존성에 따라 자연스럽게 조정합니다.
- 파라미터 누락, enum 허용값, 숫자 범위, 식별자 형식처럼 DB 접근 없이 확인 가능한 검증은 먼저 수행합니다.
- 상위 대상이 없거나 처리 불가능한 상태라면 하위 목록, 대량 데이터, 집계처럼 비용이 큰 조회를 수행하지 않습니다.
- 이후 처리의 게이트가 되는 대상과 조건을 먼저 확인한 뒤 종속 데이터를 조회합니다.
- 검증 데이터가 서로 의존하면 호출 횟수를 줄이기 위해 의미가 분명한 단계 단위로 묶습니다.
- 조회 순서는 기능 정합성뿐 아니라 불필요한 DB·외부 연동 비용을 줄이는 서비스 품질 기준으로 봅니다.

## 7) 트레이드오프 기록 원칙
- Pros / Cons / Alternatives / Decision 근거를 남깁니다.
- 복잡도, 운영 비용, 성능 비용과 기대 이득을 함께 기록합니다.
- 큰 결정은 `notes.md` 또는 ADR 링크로 추적 가능하게 유지합니다.

## 8) 리스크 체크
- 변경 범위가 넓으면 단계 분리 여부를 판단합니다.
- 기존 API, 데이터, 배치 호환성을 유지하거나 깨지는 지점을 명시합니다.
- 롤아웃 순서, 롤백 포인트, 모니터링 신호를 함께 기록합니다.

