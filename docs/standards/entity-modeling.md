# 엔티티/DTO 모델링 규칙

본 문서는 회사 내부 DTO/StatusDTO 기반 백엔드 프로젝트에서 엔티티를 도출하고 모델링할 때 사용하는 기준입니다.
대상 프로젝트가 다른 스택을 사용하더라도 소유 경계, 접근 패턴, 상태/이력 분리 원칙은 동일하게 적용합니다.

## 1) 엔티티 설계 원칙
### 1.1 엔티티 도출 및 분류
- 업무 문서, 화면, 정책 문서에서 명사를 추출해 후보 엔티티를 만듭니다.
- 추출된 명사는 유형(실체/마스터)과 무형(프로세스/상태)으로 구분합니다.
- 상태 전이를 일으키는 행위는 엔티티가 아니라 서비스/로직에 둡니다.

### 1.2 소유 주체와 경계 확정
- 먼저 "누가 소유하는 상태인가"를 결정합니다.
- 소유 주체가 다르면 별도 엔티티로 분리합니다.
- 설정/정책은 도메인 상태와 분리해 별도 엔티티로 둡니다.

### 1.3 읽기 패턴 기반 구조 결정
- 엔티티가 어떻게 읽히는지 먼저 정하고 키/행 구조를 설계합니다.
- 항상 함께 읽히는 값은 단일 Row를 우선 검토합니다.
- 특정 레벨/구간/상태별로 부분 조회되는 값은 다중 Row를 우선 검토합니다.

### 1.4 키와 식별자 설계
- 키 순서는 접근 패턴을 따릅니다.
- 시간/이력 조회가 중요하면 날짜나 시점을 키에 포함합니다.
- 복합키는 실제 조회 순서와 clustered index 이점을 근거로 선택합니다.

### 1.5 상태/정책/이력 분리
- 상태 전이가 잦고 이력이 필요한 데이터는 로그성 엔티티로 분리합니다.
- 규칙, 기준값, 관리자 설정은 운영 테이블과 분리합니다.

## 2) DTO/StatusDTO 기반 모델 관례
- Entity는 영속성 모델, DTO는 계층/경계 간 전달 모델, VO는 불변 값 객체로 구분합니다.
- 업데이트 가능한 엔티티는 기본적으로 `DTO`를 사용합니다.
- 상태값이 핵심인 엔티티는 `StatusDTO`를 사용해 `status` 표현을 통일합니다.
- 응답 전용 모델은 저장/갱신 책임을 갖지 않습니다.
- 공통 시간 컬럼은 `crtDate`, `updDate` 기준으로 맞춥니다.
- 로그 엔티티는 insert-only를 전제로 하고 `updDate`는 제외합니다.
- 직렬화 필드는 스키마와 애플리케이션 모델의 책임 경계를 문서화합니다.

## 3) 컬럼과 필드 매핑
- 엔티티 필드는 테이블 컬럼과 1:1 매핑을 우선합니다.
- 파생/가공 값은 엔티티보다 서비스/뷰 모델에서 계산합니다.
- DB는 `snake_case`, 애플리케이션 필드는 `camelCase`를 기본으로 사용합니다.

## 4) 상태/플래그 규칙
- boolean 성격 필드는 `YN` enum 또는 프로젝트 표준 불리언 타입을 사용합니다.
- 필드명은 `lockYN`, `useYN`처럼 의미가 드러나게 유지합니다.
- `status`에 들어갈 수 있는 값 목록과 각 값의 의미는 문서와 모델에서 함께 관리합니다.

## 5) 직렬화/비매핑 필드
- 구조화된 객체/목록 저장이 필요할 때 `@JsonColumn` 또는 동등한 직렬화 필드를 사용합니다.
- JSON 컬럼은 기본 조회 키가 아닌 보조 정보에 제한합니다.
- DB 컬럼과 직접 매핑하지 않는 계산/참조 필드는 `@IgnoreColumnProperties` 또는 동등한 방식으로 제외합니다.

## 6) 네이밍 규칙
- 클래스명은 단수형 명사를 기본으로 합니다.
- 로그성 엔티티는 `*Log`, 읽기 로그는 `*Rlog` 패턴을 사용합니다.
- 식별자 필드는 `teamId`, `playerId`, `itemId`처럼 `Id` 접미를 사용합니다.
- 코드성 값은 `xxxCode` 패턴을 사용합니다.

## 7) 어드민/운영 메타 패턴
- 어드민 제공 모델은 `@BeanMeta`, `@PropertyMeta(key = true)` 같은 메타 정보 사용 여부를 검토합니다.
- 캐시/메뉴/권한 메타는 모델과 관리자 계층에 일관되게 배치합니다.
- CRUD와 운영 검증 책임은 `Editor` 계층 또는 프로젝트 표준 관리 컴포넌트에 둡니다.

## 8) 로그 DB 설계 규칙
- 로그 엔티티는 insert-only로 설계합니다.
- 읽기 로그와 적재 전용 로그는 저장소와 네이밍을 구분합니다.
- 로그성 테이블은 운영 조회 의존성을 최소화하고, 감사 목적을 분명히 합니다.

## 9) 모델링 체크리스트
- 엔티티 경계와 소유 주체가 명확한가
- DTO / StatusDTO 선택 기준이 분명한가
- 키 순서가 접근 패턴과 일치하는가
- JSON 컬럼을 보조 데이터로만 사용했는가
- 계산/참조 필드를 분리했는가
- 상태, 정책, 이력을 분리했는가
