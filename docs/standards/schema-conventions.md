# DB 설계 관례(MySQL)

이 문서는 회사 공통으로 사용하는 DB(MySQL) 스키마 설계 관례를 정의합니다.

## 1) 적용 원칙과 예외
- 본 문서는 SVD의 DB 설계 기본 SSOT입니다.
- 에이전트 문서, 템플릿, 기능 문서는 본 문서를 우선 참조하고 중복 규칙 복사를 최소화합니다.
- 대상 프로젝트의 기존 운영 스키마와 충돌하는 경우, 호환성/운영 안정성을 우선하고 예외 사유를 `schema.sql` 또는 `notes.md`에 기록합니다.
- 예외 기록에는 이유, 영향 범위, 호환성 영향, 롤백 포인트를 포함합니다.

## 2) 공통 규칙
- 테이블/컬럼명은 `snake_case`를 사용합니다.
- 테이블명은 단수형(singular)을 사용합니다. (예: `user`, `match`, `season`)
- 스토리지 엔진은 `InnoDB`를 사용합니다.
- 테이블 기본 문자셋/콜레이션은 `CHARSET=utf8mb4 COLLATE=utf8mb4_bin`을 사용합니다.
- 기본키는 **기본적으로 단일 컬럼 PK**를 우선합니다. 다만 조회/접근 패턴과 InnoDB clustered index 활용 목적이 명확한 경우 **복합 PK(Composite PK)** 를 사용할 수 있습니다.

## 3) 네이밍/식별자 규칙
- 엔티티 식별자는 타입에 따라 아래 규칙을 우선합니다.
  - 숫자형 식별자: `xxx_id`
  - 문자열형 식별자: `xxx_code`
- boolean 의미 컬럼은 숫자(0/1)를 사용하지 않고, 접미사로 `_yn`을 사용합니다.
  - 타입은 `CHAR(1) NOT NULL`을 사용하며 값은 `Y` 또는 `N`만 사용합니다.
  - 예: pickup 가능 여부 → `pick_yn`
  - 도메인/엔티티 레벨에서는 `YN` enum(`Y`/`N`)으로 매핑합니다.

## 4) 숫자 타입 규칙
- 컬럼 정의 시 예상되는 증가 수치 및 사용 용도를 고려하여 numeric 타입을 설정합니다. (예: `TINYINT`, `INT`, `BIGINT`)
- 음수가 명확히 필요 없는 경우는 `UNSIGNED` 옵션을 추가하여 양수만 사용합니다.
- `AUTO_INCREMENT` 키 사용 시 항상 `UNSIGNED`로 사용합니다.

## 5) 문자 타입 규칙
- 컬럼 정의 시 예상되는 문자열 크기를 검토 후 그에 맞게 사이즈를 설정합니다. (예: `VARCHAR(20)`)
- 명백히 고정된 길이로 사용될 경우 `CHAR(n)` 타입을 사용합니다. (예: `xxx_yn CHAR(1)`)

## 6) DEFAULT 규칙
- 기본값으로 넣을 수 있는 값이 있다면 `DEFAULT`를 지정합니다.

## 7) NULL/NOT NULL 규칙
- 의미상 `NULL`이 필요한 경우를 제외하고는 `NOT NULL`로 설정합니다.
- `NULL` 컬럼은 컬럼당 추가 메타 데이터가 필요하며, `NULL` 컬럼에 대한 인덱스는 비효율적일 수 있습니다.

## 8) JSON 직렬화 컬럼 규칙
- 컬럼에 객체를 JSON으로 직렬화하여 저장하는 경우, 컬럼 타입은 `TEXT`를 사용합니다.
- 해당 컬럼은 “JSON 직렬화 데이터”임을 테이블 스펙 문서에 명시합니다.

## 9) `status` 컬럼 규칙
- `status`는 엔티티의 상태를 나타내며, 어떤 값들만 들어갈 수 있는지 목록을 테이블(엔티티)별로 정의합니다.
- 기본 값 집합은 `OK`/`BLIND`/`DEL` 입니다.
  - `OK`: 정상(사용 가능)
  - `BLIND`: 노출/사용 제한(블라인드)
  - `DEL`: 삭제(논리 삭제)
- 진행 상태가 중요한 엔티티는 `READY`/`PLAYING`/`DONE` 등 “도메인 상태값”을 `status`로 사용할 수 있습니다.
- `status`에 들어갈 수 있는 값 목록이 `OK`/`BLIND`/`DEL` 이외인 경우에는 해당 테이블 스펙 문서에 “허용 값 목록과 의미(및 기본 조회/필터링 기준)”를 반드시 명시합니다.
- 논리 삭제가 필요한 테이블은 허용 값 목록에 `DEL`을 포함하는 것을 권장합니다.

## 10) 타임스탬프 컬럼 규칙
- 업데이트 가능한 테이블은 마지막 컬럼에 아래를 둡니다.
  - `crt_date` `DATETIME`: 생성 일시
  - `upd_date` `DATETIME`: 수정 일시
- `crt_date`, `upd_date`는 공통 컬럼이며 가능한 모든 “업데이트 가능 엔티티 테이블”에 적용합니다.
- 로그성 데이터처럼 **insert만 존재하고 update가 없는 테이블**은 마지막 컬럼에 `crt_date`만 둡니다.

## 11) 시간 타입 규칙
- 시간 값을 나타내는 컬럼은 `DATETIME`을 사용합니다.

## 12) 금액 타입 규칙
- 결제 상품 등 “달러 표기”가 필요한 금액은 `DECIMAL`을 사용합니다.

## 13) 키/인덱스 규칙
- 인덱스는 “소유 테이블 + 컬럼 구성”이 이름으로 드러나야 합니다.
  - 일반 인덱스: `idx$TableName$ColumnName1$ColumnName2...`
    - 예: `idx$player$player_type$cost$pick_yn`
  - 유니크 인덱스: `uidx$TableName$ColumnName1$ColumnName2...`
- InnoDB의 clustered index 특성을 고려하여, 조회 패턴에 따라 **복합키(Composite Key)** 를 사용할 수 있습니다.
  - 예: `PRIMARY KEY (user_id, season_id)` 또는 `PRIMARY KEY (user_id, shard_key)`
- 복합키를 사용하는 경우에도 “해당 엔티티의 식별/접근 패턴”에 맞게 키 순서를 결정합니다.

## 14) Foreign Key 제약(FK) 사용 방침
- 과거에는 데이터 정합성을 위해 FK 제약을 사용했으나, 사용량/동시성이 증가하면서 FK 체크 및 락 획득으로 인한 지연/데드락 리스크가 커질 수 있어 **현재는 테이블 정의에서 FK 제약을 가급적 사용하지 않는 방향**을 기본으로 합니다.
- 정합성은 가능한 한 **비즈니스 로직(서버)** 에서 트랜잭션과 검증 로직으로 보장합니다.
- FK를 사용하지 않더라도 아래는 권장합니다.
  - 참조 컬럼은 유지하고, 조회 패턴에 맞게 인덱스를 둡니다(논리적 참조 관계 유지).
  - 삭제는 논리 삭제(`status='DEL'`)를 우선하고, 참조 관계의 정합성은 서비스 레이어에서 보장합니다.

## 15) DB 분리 정책
- 게임 DB는 아래 2종으로 분리하여 운영합니다.
  - **Data DB**: 일반 데이터 저장(비즈니스 로직의 읽기/쓰기 대상)
  - **Log DB**: 로그 전용 저장(INSERT 전용)
- Log DB는 **순수 로그 적재 목적**으로만 사용하며, 비즈니스 로직에서 조회/조인 등 읽기 의존을 두지 않습니다.

## 16) 로그 테이블 규칙(네이밍/배치/PK)
- 로그 테이블은 접미사로 로그 성격과 배치 위치를 구분합니다.
  - `*_log`: Log DB에 위치하는 INSERT 전용 로그 테이블
  - `*_rlog`: 읽기가 필요한 로그(readable log) 테이블이며 Data DB에 위치
- `*_log` 테이블 PK 관례
  - 기본 PK 컬럼명: `{table}_log_id` (예: `match_log` → `match_log_id`)
  - 기본 타입: `INT UNSIGNED NOT NULL AUTO_INCREMENT`
  - 로그 규모가 큰 경우(또는 클 수 있는 경우): `BIGINT UNSIGNED NOT NULL AUTO_INCREMENT` 사용 가능
- 로그 테이블에서 “로그의 종류” 컬럼은 보통 `log_type`을 사용합니다.

## 17) 예외 허용 기준
- 기존 운영 테이블과 타입, charset, collation, PK 규약을 맞춰야 하는 경우
- 공통 라이브러리/ORM/배치가 특정 컬럼 타입이나 이름을 전제하는 경우
- 데이터 마이그레이션 비용이나 롤백 리스크가 전역 기본값 적용보다 큰 경우
- 외부 시스템 또는 다른 서비스와 공유하는 계약을 유지해야 하는 경우
