# 테스트 가이드라인

본 문서는 SVD 기반 구현에서 테스트 설계와 작성 규칙을 통일하기 위한 공통 기준입니다.

## 1) 기본 원칙
- 유닛 테스트는 핵심 메서드 기준으로 필수 작성합니다.
- 통합 테스트는 핵심 서비스와 DAO 레이어를 우선합니다.
- 테스트 작성 순서는 `unit -> DAO -> service`를 기본으로 합니다.
- 경계값, 예외, 상태 전이 테스트를 필수로 포함합니다.
- 테스트는 재현 가능하고 결정적으로 동작해야 합니다.
- 개발 완료 후 반드시 테스트를 실행하고 결과를 기록합니다.
- 테스트 범위는 변경된 코드 실행 경로와 실제 사용자 흐름을 함께 기준으로 잡습니다.
- 버그 수정으로 기존에 동작하던 경로가 깨진 것이 확인되면 동일 시나리오를 잡는 회귀 테스트를 필수로 추가합니다.
- 테스트 실패는 `현재 변경으로 인한 실패`, `기존에 존재하던 실패`, `판단 불가`로 분류합니다. 판단이 모호하면 `현재 변경으로 인한 실패`로 처리합니다.

## 2) 테스트 범위
- 유닛: 로직, 유틸, 검증 함수
- 통합: 서비스, DAO 구현체
- E2E: 인증, 결제, 핵심 업무 흐름 등 중요한 사용자 플로우만 제한적으로 적용
- 여러 컴포넌트/서비스를 가로지르는 일반 사용자 흐름, mock이 실제 실패를 숨길 수 있는 통합 경로, 데이터 파괴 가능 흐름은 통합 또는 E2E 쪽을 우선 검토합니다.
- 입력/출력이 명확한 순수 함수, 내부 helper, 단일 메서드의 엣지 케이스는 유닛 테스트를 우선합니다.

## 3) 실패 분류 예시
- 변경한 서비스, DAO, API, 상태 전이 경로를 직접 타는 실패는 `현재 변경으로 인한 실패`
- 현재 작업 범위와 무관하고 기존 브랜치나 기준 환경에서도 재현되는 실패는 `기존에 존재하던 실패`
- 공용 인프라 불안정, 외부 환경 문제, 증거 부족으로 원인을 단정하기 어려우면 `판단 불가`

## 4) 필수 엣지 케이스
- null, empty 입력
- 최소값, 최대값, 잘못된 타입/포맷
- 권한 실패와 상태 전이 오류
- 중복 요청, 멱등성, 동시성 충돌 가능 구간

## 5) 테스트 작성 원칙
- 테스트는 실패 이유가 명확해야 합니다.
- 실패 시 원인을 빠르게 파악할 수 있도록 단언과 메시지를 명확히 작성합니다.
- 외부 시스템(DB/캐시/메시지 브로커/API)은 테스트 목적에 맞게 Mock, Stub, Testcontainer 등으로 격리합니다.
- 테스트 데이터는 재사용 가능하게 분리합니다.
- 테스트는 독립적으로 실행되어야 합니다.
- 하나의 테스트는 하나의 목적만 검증합니다.
- 테스트 안에서 반복문으로 많은 케이스를 한 번에 검증하는 패턴은 지양합니다.

## 6) 안정성/플레이키 대응
- 불안정 테스트는 원인을 분석한 뒤 보강합니다.
- 시간, 랜덤, 외부 상태는 반드시 제어 가능한 방식으로 바꿉니다.
- 타이밍 의존 코드는 조건 기반 대기를 우선하고, sleep은 마지막 수단으로만 사용합니다.
- DB의 `crt_date`, `upd_date`는 서버 시간을 사용하므로 직접 set으로 제어하지 않습니다.
- 시간 의존 로직은 프로젝트의 서버 시간 유틸 또는 테스트 훅으로 고정합니다.

## 7) 작성 스타일
- Given / When / Then 또는 Arrange / Act / Assert 구조를 사용합니다.
- 리플렉션 기반 주입은 지양하고, 생성자 또는 테스트 프레임워크 주입을 우선합니다.
- 파일명은 대상 클래스명 + `Test`
- 메서드명은 `whenX_thenY` 또는 `shouldX`
- 공통 픽스처는 테스트 지원 패키지(빌더/팩토리)로 추출해 중복을 줄입니다.
- 줄바꿈과 메시지는 실패 원인이 바로 보이도록 작성합니다.
