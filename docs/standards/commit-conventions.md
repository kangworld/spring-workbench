# 커밋 메시지와 범위 규칙

## 1) 권한

- 사용자가 명시적으로 요청한 경우에만 stage, commit, amend를 수행합니다.
- commit 요청은 push, PR, merge와 branch 정리 승인까지 포함하지 않습니다.
- 기존 staged 변경과 사용자 수정은 이번 작업 파일과 구분합니다.
- 서로 다른 리뷰 목적의 변경을 한 commit에 섞지 않습니다.

## 2) 형식 결정

- 대상 저장소에 기존 규칙이 있으면 그 규칙을 우선합니다.
- 규칙 문서가 없으면 최근 commit subject에서 실제 반복 형식을 확인합니다.
- 근거가 부족하면 새로운 prefix 체계를 임의로 만들지 않고 간결한 의미 중심 subject를 사용합니다.
- 프로젝트가 의미 기반 말머리를 사용하면 `[영역] 변경 요약` 형식을 적용할 수 있습니다.

```text
[Order] 주문 취소 시 재고 복구 연결
[Payment] 결제 승인 중복 요청 방지
[Docs] 프로젝트 실행 환경 규약 정리
```

## 3) 말머리 선택

- 말머리는 변경 파일 수나 기술 계층이 아니라 변경의 핵심 도메인·책임을 나타냅니다.
- domain table, repository, service, API와 test를 함께 바꾸면 해당 domain 말머리를 사용합니다.
- 코드와 그 테스트를 함께 바꾸면 기능 영역을 사용하고 test만 바꿀 때만 test 영역을 사용합니다.
- 구현과 문서가 같은 기능 변경을 설명하면 기능 영역을 사용하고 문서만 바꿀 때만 docs 영역을 사용합니다.
- 여러 영역이 함께 바뀌어도 핵심 상태 변경이나 계약을 소유하는 영역 하나를 우선합니다.
- 두 영역의 계약을 분리할 수 없는 연결 작업만 조합 말머리를 검토합니다.
- 로컬 작업 번호와 에이전트 계획 ID를 commit subject, 코드, 주석, SQL과 로그에 사용하지 않습니다.

## 4) 요약 작성

- 무엇이 달라졌는지 현재형 한 줄로 작성합니다.
- 마침표를 붙이지 않습니다.
- `수정`, `작업`, `반영`만으로 끝내지 않고 사용자나 시스템 관점의 변화를 드러냅니다.
- 구현 방법보다 결과를 우선하되 migration이나 보안 변경처럼 방법 자체가 위험 경계인 경우 이를 명시합니다.

워스트:

```text
[Service] 코드 수정
F12 작업 반영
```

베스트:

```text
[Order] 취소 완료 시 예약 재고를 원자적으로 복구
```

## 5) 범위 검증

commit 전에 다음을 확인합니다.

- staged 파일이 이번 승인 범위와 일치하는가
- 제품 코드, 테스트와 필수 계약 문서가 함께 포함됐는가
- `.local`, 로컬 심볼릭 링크, 비밀값, 실행 로그와 agent 작업 초안이 제외됐는가
- formatter나 생성 파일이 의도하지 않은 대량 변경을 만들지 않았는가
- 관련 검증 결과를 성공으로 보고할 근거가 있는가
