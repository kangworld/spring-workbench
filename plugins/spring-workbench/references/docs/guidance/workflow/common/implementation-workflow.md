# 구현 작업 흐름

## 1) 작업 시작 게이트

구현 전에 다음을 완료합니다.

1. 대상 저장소와 영향받는 모듈의 브랜치·dirty 상태를 확인합니다.
2. 관련 요구사항, API, DB, 아키텍처 문서와 적용 우선순위를 확인합니다.
3. 작업 문서에서 목표, 완료 조건, 포함·제외 범위와 미정 사항을 확인합니다.
4. 현재 프로젝트의 같은 계층 구현과 테스트를 먼저 확인합니다.
5. 익숙하지 않은 기술이나 패턴은 기존 표준, 내장 기능, 운영 선례와 유사 프로젝트를 조사합니다.
6. 후보 모듈은 이름으로 추정하지 않고 public API, 설정, bean 등록, 실제 소비자를 확인합니다.
7. 신규 baseline SQL이 범위에 있으면 최초 DDL, 전체 변경 SQL, Git 이력과 기준 DB를 대조해 최종 스키마 근거를 정리합니다.
8. 모듈을 재사용하거나 변경하면 dependency tree로 실제 유입 경로, 요청·선택 버전과 runtime 호환 위험을 확인합니다.
9. API 제거나 버전 충돌 위험이 있으면 compile된 의존성과 최종 runtime classpath의 binary linkage를 확인합니다.
10. reflection, annotation, auto-configuration, serialization처럼 정적 분석으로 보장할 수 없는 경로는 runtime 테스트 계획을 세웁니다.

작업 문서는 `feature-work-document.md`의 간결한 형식을 따릅니다. 상세 조사 과정과 전체 파일 목록을 복사하지 않고 범위 결정에 영향을 주는 결론만 기록합니다.

## 2) 승인 게이트

- 큰 기능은 구현 전에 작업 단위, 영향 범위와 위험을 공유합니다.
- 코드, DB, 공통 모듈, 버전, 외부 계약 변경은 승인된 범위 안에서만 수행합니다.
- 질문, 근거 확인과 리뷰 요청은 파일 변경 승인으로 해석하지 않습니다.
- 이전 지시가 철회되거나 범위가 좁아지면 최신 지시만 적용합니다.
- 미정 정책을 안정성이나 일반 관례를 이유로 임의 확정하지 않습니다.
- 예시 이름과 값은 요구사항이 아닙니다. 실제 계약에 존재하는지 확인합니다.
- 승인 범위 밖의 문제는 우회 코드로 숨기지 않고 원인, 영향과 선택지를 공유합니다.

## 3) 계약 문서 게이트

- 구현에 필요한 요구사항, API, DB 또는 아키텍처 계약이 없거나 현재 구현과 충돌하면 `계약 없음`, `표현이 모호함`, `현재 구현 불일치`를 구분합니다.
- 계약 변경이 필요하면 공백, 변경할 계약과 영향 범위를 먼저 공유하고 승인 후 해당 계약의 소유 저장소에서 수정합니다.
- 구현 메서드나 내부 모듈 API를 제품 계약으로 승격하지 않습니다.
- 계약 확정이 구현 방향에 영향을 주면 계약이 확정될 때까지 해당 구현을 진행하지 않습니다.
- 구현 후 동기화만 필요한 문서는 구현 검증을 마친 뒤 갱신하고 코드·DB·API와 다시 대조합니다.

## 4) 구현 중 게이트

- 승인된 단계 하나를 완료하고 집중 검증한 뒤 다음 단계로 넘어갑니다.
- 서로 다른 리뷰 목적의 변경을 한 단계에 누적하거나 여러 단계에 걸친 미완성 공개 동작을 남기지 않습니다.
- 단계별 리뷰를 요청받으면 단계 종료 시 변경 범위와 검증 결과를 공유합니다.
- 새 이름, 설정 키, 패키지, interface, Properties, wrapper, context와 helper를 만들기 전에 기존 패턴으로 해결할 수 있는지 확인합니다.
- 문서 분류명은 코드 패키지 소유권으로 간주하지 않습니다.
- 공통 모듈 변경은 현재 기능만 통과시키는 것으로 끝내지 않고 기존 소비자의 설정 키, bean 이름과 public API 호환을 확인합니다.
- 신규 환경용 SQL은 전체 스키마 이력을 계산한 최종 baseline으로 작성하고 운영 메타·정책 DML을 섞지 않습니다.
- Git 이력에서 계산한 스키마와 기준 DB가 다르면 임의 선택하지 않고 적용 기준을 확정합니다.
- 기존 미커밋 변경, staging, commit과 branch는 명시적 요청 없이 정리하거나 되돌리지 않습니다.
- 기능 변경과 직접 관계없는 대규모 리팩터링은 별도 작업으로 분리합니다.

## 5) 완료 게이트

구현 요청에는 변경에 필요한 테스트 작성·보완과 실행이 포함됩니다. 코드 변경을 마친 뒤 다음 순서로 확인합니다.

1. `spring-backend-verification`으로 변경된 동작을 보호할 테스트를 작성하거나 보완하고 실행합니다. 프로젝트의 테스트 명령과 검증 기준을 적용합니다.
2. `spring-backend-implementation-audit`으로 최종 구현을 프로젝트 계약과 적용 지침에 대조합니다. 이어서 `spring-backend-test-audit`으로 테스트가 필요한 시나리오와 실패 조건을 검증하는지 확인합니다. 테스트가 통과했어도 두 검증을 수행합니다.
3. 발견한 문제 중 요청 범위에서 해결할 수 있는 것은 구현이나 테스트를 수정합니다. 관련 테스트를 다시 실행하고 최신 변경에 대해 두 검증을 다시 수행합니다. 수정 가능한 문제가 남아 있으면 같은 순서로 확인합니다.
4. 계약이 미정이거나 환경 제약으로 확인할 수 없는 항목은 근거와 영향 범위를 완료 보고에 남깁니다. 검증은 현재 구현 작업의 일부로 진행합니다.

완료 전에 다음을 함께 확인합니다.

1. 계약 동기화
   - 요구사항, API, DB와 서버·소비자 동작이 일치하는가
   - DDL, baseline SQL과 적용 후 실제 테이블·인덱스가 일치하는가
2. 구현 품질
   - 공개 동작이 완전히 연결되었고 실패 경로와 엣지 케이스가 닫혔는가
   - 핵심 로직의 의도, 제약과 운영상 주의점이 주석으로 드러나는가
3. 테스트·검증
   - 관련 테스트, 영향 영역 회귀와 위험에 비례한 전체 검증을 수행했는가
   - 실행하지 못한 검증과 이유를 구분했는가
4. 후속 작업
   - 실제 사용처나 선행 계약 때문에 미룬 구체 기능이 있는가
   - 일반 기술 부채나 테스트 환경 문제를 후속 기능으로 잘못 분류하지 않았는가

## 6) 완료 보고

- 변경한 저장소와 파일 범위
- 구현한 동작과 제외한 동작
- 요구사항과 작업 문서 갱신 여부
- 실행한 정확한 검증 명령과 결과
- 구현 준수와 테스트 품질의 최종 검증 결과
- 실행하지 못한 검증과 이유
- 남은 미정 사항과 운영 위험
- Git 상태 변경 여부

테스트가 통과하지 않았거나 실행하지 못했으면 성공으로 표현하지 않습니다. 기존 실패와 이번 변경으로 생긴 실패를 구분합니다.

## 7) 커밋 통제와 메시지

- 사용자의 명시적 승인이 없으면 commit, amend, staging, branch 변경, push, PR 또는 merge를 수행하지 않습니다.
- 커밋을 요청받으면 [커밋 규약](../git/commit-conventions.md)에서 대상 저장소의 기존 형식 확인, 변경 범위 분리와 메시지 작성 기준을 적용합니다.
