# 피처 작업 문서 규약

## 1) 목적과 기본 형식

작업 문서는 구현 범위와 짧은 리뷰 단위를 빠르게 합의하기 위한 문서입니다. 하나의 피처는 기본적으로 한 문서에서 관리하며 요구사항 본문, 조사 과정, 전체 파일 목록, 명령 출력과 일별 진행 기록을 복사하지 않습니다.

작은 작업은 한 화면, 큰 작업도 필요한 구현 단계와 경계를 빠르게 훑을 수 있는 분량을 우선합니다.

```markdown
# {피처 ID} {작업명}

- 상태: 검토 초안 | 승인 완료 | 구현 중 | 구현 완료 | 검증 완료 | 보류

## 목표와 범위

- 사용자가 얻게 되는 동작:
- 완료 조건:
- 포함:
- 제외:
- 관련 요구사항:

## 구현 단계

### Step 1. {독립적으로 리뷰할 수 있는 결과}

- 결과:
- 변경 경계: 공개 계약, 상태 소유자, 주요 패키지만 필요한 경우 작성
- 검증:

### Step 2. ...

- 결과:
- 변경 경계:
- 검증:

## 결정 필요

- 지금 구현을 막는 제품 정책이나 외부 변경 승인만 작성
```

## 2) 단계 나누기

- 한 단계는 리뷰어가 한 가지 동작이나 계약에 집중해 판단할 수 있는 단위로 잡습니다.
- model, DAO, service, handler처럼 계층만 기준으로 기계적으로 나누지 않습니다.
- 한 동작에 필요한 저장, 연결과 집중 테스트는 같은 단계에 둡니다.
- 각 단계는 앞 단계에만 의존하며 완료 시 깨진 컴파일이나 절반만 연결된 공개 동작을 남기지 않습니다.
- 보통 3~7단계를 출발점으로 삼고 서로 다른 계약을 한 번에 판단해야 하면 나눕니다.
- 독립 의미가 없는 준비 코드만 남으면 앞뒤 단계와 합칩니다.
- 기능과 직접 관계없는 정리나 리팩터링은 리뷰 목적이 다를 때만 별도 단계로 둡니다.
- 미래 재사용만 예상한 추상화 단계는 만들지 않습니다.
- 단계는 자연스러운 커밋 후보가 될 수 있지만 커밋 승인을 뜻하지 않습니다.
- 독립된 계약 승인, 저장소, 배포·롤백 경계가 있을 때만 하위 문서로 분리합니다.

## 3) 변경 경계 작성

- 모든 변경 클래스를 표로 나열하지 않습니다.
- 새 공개 계약, 상태 전환 소유자, 트랜잭션 경계, DB·API·설정 영향처럼 리뷰 판단에 필요한 내용만 적습니다.
- 기존 패턴으로 충분하면 신규 추상화나 얇은 위임 계층을 계획하지 않습니다.
- 현재 사용처 하나의 정책은 상위 use-case에 캡슐화하고 실제 중복이 생길 때 추출합니다.
- 후속 기능을 미리 구현하지 않고 현재 단계가 제공할 공개 메서드와 상태 불변식까지만 적습니다.
- 관련 계약 문서는 경로만 연결하고 본문을 반복하지 않습니다.

## 4) 구현 후 갱신

계획을 장문의 구현 보고서로 바꾸지 않고 단계별 결과와 최종 검증만 덧붙입니다.

```markdown
## 결과

- Step 1: 완료 | 변경 | 보류 — 계획과 달라진 내용이 있을 때만 한 줄
- Step 2: ...

## 검증 결과

- 실행한 검증과 결과:
- 실행하지 않은 검증과 이유:

## 남은 항목

- 다음 작업에서 실제로 이어받을 내용만 작성
```

## 5) 기록 다이어트

- 코드 탐색 과정, 후보 이름, 실패한 시도, 반복 테스트 실행, Git 명령과 단순 수정 기록은 남기지 않습니다.
- 영향이 없는 항목과 빈 섹션은 삭제합니다.
- 미정 사항이 없으면 `결정 필요` 섹션을 만들지 않습니다.
- 최종적으로 신뢰할 수 있는 검증 명령과 결과만 남기고 중간 실패와 재실행 과정은 기록하지 않습니다.
- 제품 방향, 외부 합의나 되돌리기 어려운 설계 결정은 요구사항 또는 ADR 같은 최종 기준 문서에 반영합니다.

## 6) 프로젝트 일정 문서와의 경계

- 마일스톤과 기능 순서는 프로젝트 상태이므로 공통 형식을 강제하지 않습니다.
- 프로젝트에 일정 문서가 실제로 있으면 작업 시작 시 현재 작업과의 관계만 확인하고, 상세 구현 계약은 요구사항과 피처 작업 문서에서 관리합니다.
- 공통 지침을 설치한다는 이유로 마일스톤 문서를 새로 만들지 않습니다.

## 7) 후속 작업 보류 기록

대기 원장은 실제 사용처나 선행 계약이 확정된 뒤 구현하기로 미룬 구체 기능을 관리합니다. 최종 요구사항과 마일스톤을 대신하지 않습니다.

등록 기준:

- 승인된 작업에서 구체적인 개발 항목을 의도적으로 미뤘어야 합니다.
- 무엇이 확정되면 다시 시작할 수 있는지 설명할 수 있어야 합니다.
- 후속 마일스톤이 전부 소유하는 일반 구현은 중복 등록하지 않습니다.
- 기존 기능을 다시 연결해야 하는 지점은 누락 방지를 위해 등록할 수 있습니다.

등록하지 않는 항목:

- 테스트 DB나 fixture 정비, 실패한 검증 재실행
- commit, push와 branch 정리
- 막연한 개선 아이디어와 일반 운영 위험
- 구현하지 않기로 취소한 범위

상태:

- `대기`: 재개 조건이 아직 충족되지 않음
- `재개`: 별도 작업 문서를 만들고 범위를 검토하거나 구현 중
- `완료`: 후속 구현과 검증이 끝남
- `취소`: 더 이상 구현하지 않기로 결정함

```markdown
| ID | 미뤄둔 기능 | 재개 시점 | 상태 |
|---|---|---|---|
| DFR-001 | {구체 기능} | {확정되어야 할 계약 또는 사용처} | 대기 |

## DFR-001 {기능명}

- 출처:
- 미뤄둔 기능:
- 미룬 이유:
- 재개 조건:
- 재개 시 확인:
```

- 후속 작업을 시작하면 항목을 지우지 않고 상태를 `재개`로 바꾸고 새 작업 문서를 연결합니다.
- 구현이 끝나면 검증 결과가 기록된 작업 문서를 연결하고 상태를 `완료`로 바꿉니다.
- 재개할 때 과거 설명을 구현 계약으로 사용하지 않고 최신 요구사항과 현재 코드를 다시 확인합니다.
- 새 보류가 생기면 원래 작업 문서에는 원장 ID와 링크만 남기고 재개 조건은 원장에서 관리합니다.
