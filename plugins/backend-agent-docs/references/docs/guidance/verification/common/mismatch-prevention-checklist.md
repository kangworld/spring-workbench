# 미스매치 방지 체크리스트

## 1) 요청과 범위

- [ ] 질문인지 변경 승인인지 구분했는가
- [ ] 예시 이름과 값을 실제 요구사항으로 오해하지 않았는가
- [ ] 오래된 지시를 현재 작업에 자동으로 적용하지 않았는가
- [ ] 삭제 요청의 정확한 대상과 범위를 확인했는가
- [ ] 미정 정책과 제외 범위를 작업 문서에 남겼는가

## 2) 문서와 계약

- [ ] 관련 요구사항, API, DB와 아키텍처 문서를 실제로 찾았는가
- [ ] 현재 계약 문장을 읽고 `계약 없음`, `표현이 모호함`, `현재 구현 불일치`를 구분했는가
- [ ] 이미 명시된 계약을 다시 질문하거나 조건부 답변으로 덮어쓰지 않았는가
- [ ] 필요한 계약이 없거나 수정이 필요하면 공백과 영향 범위를 공유했는가
- [ ] 계약 변경을 소유 저장소와 승인 범위 안에서 수행했는가
- [ ] 내부 구현 사례를 제품 계약으로 전달하지 않았는가
- [ ] error code, null·빈 배열, 시간 단위와 response field를 기억이나 클래스명으로 추정하지 않았는가
- [ ] 서버 판단만으로 소비자 동기화 동작을 단정하지 않았는가
- [ ] 문서 분류명을 Java 패키지 소유권으로 오해하지 않았는가

## 3) 기존 구현과 구조

- [ ] 같은 계층 코드와 프로젝트 반복 패턴을 먼저 확인했는가
- [ ] application root에서 전역 `api`·`service`·`dao`·`model` 패키지로 기능 코드를 흩뜨리지 않았는가
- [ ] 기능 패키지나 포괄적인 `model` 아래에 entity, domain, use-case model과 query projection을 함께 모으지 않았는가
- [ ] JPA 영속성 클래스는 `entity`, 순수 업무 규칙·값·상태는 `domain`으로 분리했는가
- [ ] 특정 use-case 입출력은 `service/model`, query 결과 형태는 `dao/projection`, 외부 계약은 `api/request|response`에 두었는가
- [ ] `service/impl`, `dao/jdbc|jpa`, `entity`, `domain`, `exception` 경계를 책임에 따라 일관되게 적용했는가
- [ ] package 형식을 맞추기 위한 entity-domain 일대일 복제나 파일 하나짜리 하위 package를 만들지 않았는가
- [ ] 신규 영속성 영역이 JPA 기본값을 따르는가, 다른 기술이면 검증 가능한 선택 이유와 적용 범위를 기록했는가
- [ ] 테스트 패키지가 운영 코드 패키지를 그대로 따르는가
- [ ] `common`·`shared`·`util`을 책임 없는 임시 대피소로 사용하지 않았는가
- [ ] 불필요한 interface, Properties, wrapper, context와 package depth를 추가하지 않았는가
- [ ] 비슷한 상태와 use-case를 하나의 응집된 service로 구성할 수 있는지 검토했는가
- [ ] 별도 service가 독립된 도메인 책임 없이 조회 전달이나 Map 구성만 하지 않는가
- [ ] context, plan과 wallet이 데이터 보관을 넘어 조회·분기·변경·저장을 떠안지 않는가
- [ ] 각 도메인의 조회·검증·상태 변경이 해당 도메인 service에 묶여 있는가
- [ ] coordinator가 호출 순서를 넘어 조회·계획·저장을 직접 떠안지 않는가
- [ ] 객체 구성과 검증 흐름이 읽기 쉬운가
- [ ] 비대상 row를 키 수집 전에 제외했는가
- [ ] 조립 후 계산기와 factory에 조회용 Map 전체가 아니라 필요한 도메인 객체만 전달했는가
- [ ] boolean 이름과 분기가 긍정 상태를 직접 표현하는가
- [ ] 앞선 실패 뒤에 불필요한 조회, 주입과 계산을 수행하지 않는가
- [ ] 같은 상태 변경·저장·반환을 분기마다 복제하지 않았는가
- [ ] 로그가 요구하는 변경 전·후 스냅샷과 생성 순서를 검증했는가
- [ ] 마지막 저장 실패가 부분 성공을 남기지 않는가
- [ ] `coding-conventions.md`의 주석 품질 검증 기준을 변경한 Java 파일 전체에 적용했는가

## 4) 모듈과 의존성

- [ ] 모듈의 구현체·공통 계약·SPI·설정 역할을 실제 코드와 소비자로 확인했는가
- [ ] 직접 사용하지 않는다는 이유로 의존성을 불필요하다고 단정하지 않았는가
- [ ] 프레임워크 호환 문제를 임시 의존성으로 덮지 않았는가
- [ ] 현재 기능에 필요한 최소 모듈과 소비 연쇄만 변경 범위로 올렸는가
- [ ] dependency tree로 실제 유입 경로와 요청·선택 버전을 확인했는가
- [ ] API 제거나 버전 충돌 위험이 있으면 class·method·field linkage를 확인했는가
- [ ] reflection, annotation, auto-configuration과 serialization 경로를 runtime 테스트로 확인했는가
- [ ] exclusion 위치를 영향 범위와 승인에 맞게 결정했는가

## 5) 설정과 런타임

- [ ] 실제로 존재하는 유효한 설정 키를 사용했는가
- [ ] 설정 소비 코드와 property loading 경로를 확인했는가
- [ ] override 값과 유지되는 default 값을 실제 context로 검증했는가
- [ ] 같은 bean 이름에서 구현 타입이 달라지는 경로를 구분했는가
- [ ] 설정으로 해결할 수 없는 구조적 문제를 설정으로 가리지 않았는가

## 6) DB baseline SQL

- [ ] 확정 DDL과 현재 스키마의 차이와 영향을 확인했는가
- [ ] 저장소 전체와 Git 이력에서 최초 DDL과 모든 변경 SQL을 찾았는가
- [ ] 최초 DDL에 변경을 시간순으로 적용해 최종 형태를 계산했는가
- [ ] 타입·길이·signed·NULL·default·PK·인덱스·unique·FK·engine·charset·collation을 대조했는가
- [ ] 현재 Java 모델만 보고 스키마를 추정하지 않았는가
- [ ] 적용하는 [DB 엔진 지침](../../persistence/README.md)에 따라 기준 DB의 실제 테이블 정의와 인덱스를 확인했는가
- [ ] Git 이력과 실제 DB가 다르면 적용 기준을 확인했는가
- [ ] baseline SQL에는 중간 ALTER가 아니라 최종 `CREATE TABLE`만 작성했는가
- [ ] 운영 메타·정책 DML을 baseline SQL에 섞지 않았는가
- [ ] 빈 DB 적용 결과, DDL, 실제 테이블과 DAO 매핑이 일치하는가

## 7) 테스트

- [ ] 실제 bean, proxy와 transaction을 사용해야 하는 범위인가
- [ ] DAO·DB 흐름을 mock으로 가리지 않았는가
- [ ] 테스트에 네이티브 SQL을 직접 작성하지 않고 공개 계약과 test transaction을 사용했는가
- [ ] 테스트 편의를 위해 운영 조회·삭제 API를 추가하지 않았는가
- [ ] 필요한 로컬 스키마를 확정 DDL로 구성했는가
- [ ] 전체 context 대신 필요한 최소 context를 사용했는가
- [ ] mock을 명확한 외부 경계에만 사용했는가
- [ ] 테스트 이름과 설명에서 검증 의도가 드러나고 [사용 기술의 작성 기준](../README.md#기술별-검증)을 따르는가
- [ ] 핵심 임계값의 성공 경계와 바로 바깥 실패 경계를 짝으로 검증했는가
- [ ] 테스트용 전역 설정이 다른 테스트에 영향을 주지 않는가

## 8) Git과 외부 저장소

- [ ] 모든 대상 저장소의 dirty 상태를 기록했는가
- [ ] 기존 변경과 이번 변경을 구분했는가
- [ ] 명시적 요청 없이 commit, amend, reset, branch 변경과 staging을 하지 않았는가
- [ ] 사용자가 만든 변경을 덮거나 정리하지 않았는가
- [ ] 별도 요청 없이 push, PR 또는 merge로 범위를 넓히지 않았는가

## 9) 완료 동기화

- [ ] 작업 문서에 실제 구현과 검증 결과를 반영했는가
- [ ] 필요한 계약 변경을 완료하고 구현과 다시 대조했는가
- [ ] 반복 가능한 새 교훈을 적절한 기준 문서에 반영했는가
- [ ] 실행하지 않은 테스트와 남은 위험을 명시했는가
