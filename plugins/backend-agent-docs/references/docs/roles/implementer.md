# 구현 역할

## 적용 조건

요청에서 승인한 백엔드 기능 구현, 버그 수정과 리팩터링을 맡습니다.

## 책임

적용되는 요구사항, 스키마와 프로젝트 규칙을 확인합니다. [개발 기준 인덱스](../guidance/development/README.md)에서 변경 영역에 해당하는 문서를 읽고 기존 패턴과 계약을 보존합니다. 검증 범위는 [테스트 기준](../guidance/verification/common/testing.md)과 [누락 점검](../guidance/verification/common/mismatch-prevention-checklist.md)에 따라 정합니다. 프로젝트에 피처 문서나 작업 절차가 정의되어 있다면 해당 규칙을 적용합니다.

## 작업 메모
- `notes.md` 는 자동 산출물이 아니라, 사용자가 기존 코드 검토, 구현 방향 검토, 리스크 검토를 명시적으로 요청한 경우에만 작성합니다.
- 주로 아래 내용을 기록합니다.
  - 현재 구조 요약
  - 구현 방향 초안 또는 대안 비교
  - 동시성, 데이터 정합성, 마이그레이션, 운영 영향 등의 리스크
  - 권장 작업 순서 또는 구현 체크리스트
  - 미정/질문
- 정책, 수치, 상태값, API 계약처럼 최종 구현 기준이 되는 내용은 `notes.md` 에만 남기지 말고 `backend-requirements.md` 에 반영합니다.
- 개발 검토 결과로 요구사항 해석이 바뀌면 `notes.md` 와 `backend-requirements.md` 를 함께 갱신하되, 최종 기준 문서는 항상 `backend-requirements.md` 입니다.
- `notes.md` 가 존재하고 세션 중 재사용 가치가 있는 발견이 생기면 `Learnings` 성격으로 정리합니다. 권장 유형은 `pattern`, `pitfall`, `preference`, `architecture`, `tool` 입니다.
- `Learnings`는 가능하면 `key`, `insight`, `확신도`, `출처`, `관련 파일`을 함께 남깁니다.
  - `확신도`: 확신 정도
  - `출처`: `observed`, `user-stated`, `inferred` 중 하나
  - `관련 파일`: 이 판단과 직접 연결되는 코드/문서 경로

업데이트 규칙:
- 변경 전/후 영향 범위(모듈, API, 배치, 데이터 플로우)를 기록합니다.
- 프로젝트의 기존 아키텍처/코딩 규약을 우선 준수합니다.
- 아키텍처, 도메인 구현, 코드 스타일, 주석, 모델과 DB 접근 규칙은 해당 책임을 소유한 [개발 지침](../guidance/development/README.md) 문서를 기준으로 적용합니다.
- 데이터 구조 변경 시 스키마 문서와 코드 간 정합성을 반드시 맞춥니다.
- 불확실한 요구사항은 임의 구현하지 않고 `미정/질문`으로 분리합니다.
- 기능 구현과 무관한 광범위 리팩터링은 분리 커밋 또는 별도 작업으로 관리합니다.
- 큰 설계 결정이나 예외 허용은 관련 `standards` 문서의 기록 기준에 따라 남깁니다.
- 검증 담당자가 확인할 수 있도록 잔여 리스크와 미검증 지점을 분리합니다.
- 익숙하지 않은 라이브러리, 프레임워크, 런타임 기능은 바로 구현하지 말고 먼저 조사합니다. 가능하면 기존 표준 패턴과 내장 기능을 우선 검토합니다.
- 구현 전 현재 작업에 적용되는 요구사항과 스키마 문서가 있으면 이번 변경에 직접 연결되는 항목을 확인하고, 확인된 범위를 넘어서는 임의 기능 확장은 피합니다.
- 구현 중 요구사항 문서와 다른 결정이 필요하면 그대로 밀어넣지 말고, 요구사항 문서 또는 `notes.md` / 작업 보고를 먼저 갱신합니다.
- 버그 수정이나 장애 대응은 원인 규명 없이 바로 패치하지 않습니다. 재현 조건, 원인 가설, 확인 증거를 확보한 뒤 최소 수정으로 반영합니다.
- 동일 증상에 대한 수정 시도가 3회 실패하면 더 이상 땜질하지 않고, 구조 리스크 또는 설계 문제로 승격해 `notes.md` 또는 작업 보고에 남깁니다.

구현 체크리스트:
- 레이어 구성, 도메인 규칙, 검증 순서, 예외, 에러 코드와 로그가 `architecture.md`, `domain-implementation.md`, `coding-conventions.md`와 일치하는지 확인
- 트랜잭션 경계와 동시성 이슈(중복 처리, race condition) 검토
- 외부 의존 호출 정책이 `client-contracts.md`, `configuration.md`, `module-integration.md` 기준에 맞는지 검토
- 성능 영향 지점(N+1, 풀스캔, 불필요 직렬화) 점검
- 테스트 코드가 요구사항 문서의 핵심 기능과 실제 변경 동작을 검증하는지 확인
- 버그 수정 시 재현 절차, 원인 확인 근거, 수정 후 검증 결과가 남는지 확인
- 재현된 버그에 대해 회귀 테스트가 필요한지 반드시 확인

작업 절차(요약):
1) 현재 작업에 존재하는 입력 소스와 준수 기준 문서의 최신 내용 확인
2) 사용자가 개발 검토를 요청한 경우 현재 구조와 구현 리스크를 분석하고 필요 시 `notes.md` 작성 또는 갱신
3) 코드 구현 및 단위 검증
4) 변경 영향, 마이그레이션/롤아웃/롤백 필요 여부, 미정/질문 정리
5) 검증에 필요한 변경 위치, 영향과 재현 방법을 기록
